# User 代码审查与重构方案

日期：2026-11-05。本文保留首次审查时的事实快照和目标方案；源码重构已经开始，各批实际完成项、验证和剩余问题见 [重构进度](USER_REFACTOR_PROGRESS.md)。本文列出的目标不等同于已实现功能。

本方案针对用户删减后的 `MRLib/User`。现有删除保持有效，不从旧版本恢复已移除的机器人业务。本阶段先让库的代码、职责和接口成立，再推进 YAML 装配、CLI 和编辑器插件；不修改外部 `zzrobot`、`RC_02` 工程。

## 1. 本次结论

需要做的是按职责收敛实现，而不是按 C/C++ 划分新旧。

- 每项能力只有一个算法或协议实现；C/C++ 可以共用核心，薄封装可以保留。
- C++ 的数学、控制器和设备对象也需要修正，不能直接作为旧 C 代码的完整替代。
- `module` 对上提供统一能力入口；机器人几何或类型的不同由 `robotics` 模型表达，设备型号的不同由 `device` 表达。
- 具体机器人的尺寸、设备实例、安装参数、遥控映射、线程和业务状态机归项目。
- 先能用普通 C/C++ 手工装配、编译和验证一个最小项目，生成器以后生成同样的装配代码。

当前可保留的基础很多：机械臂纯算法、底盘模型选择入口、部分数学与控制组件、固定容量容器、统一底盘接口和 MRLink 的 C 协议核心。主要问题是这些基础之间仍夹着重复实现、项目配置、平台细节和不一致的行为契约。

## 3. 最终职责与依赖方向

```text
项目 app / 任务适配
        │
        ▼
      module ────────────────┐
        │                   │
        ▼                   ▼
     robotics             device
        │                   │
        └─────► component ◄─┘
                            │
                            ▼
                     少量 port 契约
                            ▲
                            │ 实现
                     STM32 BSP / board
```

图中的 `port` 是时间、收发和必要同步操作的契约，不是新的业务层。使用这些契约的组件也可以直接依赖它；具体 STM32 和 CMSIS 实现在可选适配代码中。

| 位置 | 应承担的职责 | 应移出的内容 |
| --- | --- | --- |
| `component` | 数学、控制律、滤波、估计、轨迹、容器、校验、通用命令仲裁和字节协议 | 电机型号、机器人结构、遥控拨杆含义、HAL/RTOS 调用 |
| `robotics` | 运动学、动力学、机器人空间规划、跟踪控制和约束策略 | CAN、具体电机类型、线程、遥控器 |
| `device` | 协议与设备状态、能力、安装映射、轮子/关节等执行边界 | 整机任务、机械臂固定三电机组合、隐藏全局对象工厂 |
| `module` | 组合模型和设备，处理模块命令、模式、生命周期、健康状态及输出准备 | 按车型复制的完整控制器、板级初始化、任务队列、项目参数查询 |
| `port` | 最少的时间、CAN 和同步契约，按实际需要扩展 | 万能服务定位器、动态插件框架、应用注册中心 |
| `bsp` / 项目 `board` | HAL、DMA、中断、实际引脚/总线/定时器映射 | 通用算法和机器人业务 |
| 可选 `runtime/cmsis_os2` | 线程、队列、周期调用等调度适配 | 模块算法、设备协议 |
| 项目 `app` | 遥控映射、行为状态机、对象装配、任务选择和整机协同 | 库内部算法的复制版本 |

滤波器、PID、规划器和机器人控制器可以有状态；“硬件无关”不等于“无状态”。现有 `ARCHITECTURE.md` 中将 component 统称为无状态的表述，应在实施时一并修正。

建议的目标目录如下。它表示职责归属，实施时随能力迁移移动文件，不先做一次全目录改名。


## 4. C/C++ 收敛方案

| 能力 | 主实现选择 | 处理方式 |
| --- | --- | --- |
| float 标量、限幅、角度环绕 | 小型标准 C 兼容核心 | `math/scalar.h` 提供唯一实现，`scalar.hpp` 只提供薄命名空间入口；迁移后删除 `user_math.*` |
| 矩阵、范围/传动工具 | C++ | 保留固定尺寸类型，修正求解和失败语义 |
| 基本低通/高通等滤波 | 单一滤波核心 | 先删除重复的两份 C filter 中的一份，再按实际 C 调用需要选择共享 C 核心或窄接口；不保留第三套独立公式 |
| KF/EKF、观测器 | C++ | 与基本标量滤波分离依赖，修复实例化问题 |
| PID、状态反馈、串级控制 | C++ 主接口 | 统一控制律和参数；必须保留的 C 调用只提供窄桥接，旧参数类型随调用点一起迁移 |
| AHRS、CRC、简单帧解析 | C 可以继续保留 | 去掉无关头和平台依赖，不为统一扩展名重写 |
| SPSC FIFO | C 核心 + C++ 薄封装 | 当前这种复用方向合理；修所有权和同步契约 |
| 电机 | 一套协议实现 + C++ 设备组合 | 借鉴旧 C 的完整行为，修正新实现；按协议验收后删除旧 C 电机栈 |
| BMI088、DR16 等 | C 解析/驱动核心可保留 | 分离板级收发、RTOS 通知和设备状态 |
| MRLink | C 帧核心 + 一个 C++ 类型封装 | 保留核心，合并 full/lite 重复封装，分离通道适配 |
| module | 以 C++ 组合为主 | 统一能力入口，显式配置和设备引用 |

“一个实现”约束算法和协议，不禁止标准库调用、编译期常量或薄语言包装。迁移期间可以短暂存在旧 API，但每处都要列出剩余调用者和删除条件，不建立永久 `legacy` 目录或第二套兼容库。

### 4.1 `user_math` 不能只做文件合并

当前仍被 AHRS、BMI088、DR16、旧电机、joint、CRC 和旧控制组件使用，先迁移调用再删。

- clamp、abs-clip、角度环绕误差进入 `math`。
- `MoveVector_t` 与旧 mixer 的底盘速度角色收敛到 robotics 的平面速度类型。
- `CalculateRpm()` 中的射击标定值不是数学工具。若当前没有使用者，直接删除；以后需要时由对应项目或能力提供标定配置。
- `min/max` GNU 宏、`__packed`、断言宏不应通过数学头污染所有调用者。
- `Sign()` 当前返回 0/1，不是 -1/0/1（`user_math.c:41`）；不能直接按函数名替换。
- `CircleError/CircleAdd` 只修正一个周期（`:58`、`:77`）；新接口应明确任意圈数和端点规则，迁移测试覆盖旧调用的实际输入范围。
- `InvSqrt()` 用 `long*` 重解释 float（`:17`），有别名和位宽问题；默认采用有明确输入域的标准实现，需要优化时再用已验证的实现替换。

正确性重点：

1. PID 的 anti-windup 方程需要明确。目前 C/C++ 都有候选积分参与本次输出但未提交积分状态的路径，这是需验证的设计问题，不能仅靠接口改名解决。
2. `s_curve.hpp` 第五段位置式与速度式不一致，专用同步 S 曲线只取最大时长却没有真正拉伸各轴；`cubic_blend` 的零端点加速度表述不符合一般三次 Hermite；在线梯形跨目标直接置零速度也需要验证。先用连续性、数值微分和限值测试确认，再选稳定实现。
3. `cmd_center.hpp:684` 容量满时返回重新解释的槽引用，应改为明确失败；`Freshest` 当前比较路由序号，不能当作消息时间；复制、placement-new 和销毁契约也必须明确。
4. 普通组件不引入统一虚基类来追求外观一致；按类型提供简洁的 `Config / Configure / Reset / Step或Update / Result` 即可。

## 6. BSP 与 `device` 的修改清单

### 6.1 先隔离收发和时间，再统一设备

第一批只抽必要的时间、CAN 和同步契约。纯 codec 接收原始帧、输出解码值；设备运行层接收 `now`、管理在线状态和保护；STM32 adapter 负责实际收发和 DMA。

协议不仅有封包解包。厂商 enable/disable、清错、设零、确认和握手可以留在对应协议实现，不必拆成大量小类。通用离线超时、命令有效期、温度保护和本机 PID 不应在每个厂商协议里分别复制。

`device.h` 不再通过总头传染 HAL/RTOS、全部驱动和数学。公共反馈类型按用途定义，例如 `ImuSample`，避免 BMI088 公共头反向依赖 AHRS 内部结构。

### 6.2 电机：迁移行为后删除旧栈

| 旧实现 | 必须核对、迁移的有效行为 |
| --- | --- |
| `motor_rm.*` | 逻辑编号与 CAN 地址映射；M2006/M3508/GM6020 分组；同总线共享帧合并；pending 组；一次统一 Flush；方向、多圈跟踪、sequence 去重、离线超时、安全零输出 |
| `motor_dm.*` | MIT、位置速度、速度/Hybrid 的真实支持范围；使能/禁能/清错/设零；反馈状态码和温度；方向、超时和 Relax 行为 |
| `motor_lz.*` | 扩展帧地址；状态/故障；MIT；禁能与清错；设零确认；反馈连续性和超时 |
| `motor.c/.h` | 通用状态、有效性、多圈位置与零点中真正有用的部分 |

每个协议迁移后，用同一套公共设备接口服务调用者，再删除其对应旧实现；不保留两个独立收发栈同时控制同一设备。

当前 C++ 实现需要先处理的静态问题包括：

- `rm_protocol.cpp:7` 接收把 `config.id` 当反馈 CAN ID，发送却按 1～8 逻辑编号使用；高组写槽与读槽不一致（`:14`）。配置拆出明确节点编号、反馈地址和命令组。
- RM 的 `Relax/Disable` 只清 pending，不确保清零并进入发送路径（`:13`）；安全状态不能只修改内存标志。
- RM/DM 没使用反馈 sequence/timestamp；重复读取 latest 缓存会持续认为在线。LZ 则没有本周期帧就离线；统一为按反馈时间计算健康状态。
- DM/LZ 未设置 `position_valid`；反向、累计位置、软件零点与硬件设零的状态更新不一致。
- `motor_controller.cpp:236`、`:249` 的合并/分离调用路径使用不同反馈，收敛为一个 `feedback + reference + dt → command` 执行核心。
- `SetPositionTorque` 忽略 `torque_limit`（`:391`）；旧兼容构造函数曾静默忽略参数；模板实现仅显式实例化部分公开型号，可能出现链接缺口。
- `motor_factory.hpp:43` 的每型号存储与厂家共享计数器混杂。默认由项目静态创建对象并传引用，工厂不再偷偷管理全局设备容量。
- 型号描述按厂商组织，区分协议量程、额定/峰值参数、内置减速比与外部安装传动。不要用额定参数猜测协议量程。

### 6.3 Wheel、Joint 与控制权

保留小型 `WheelDevice` 接口的方向，去掉 `wheel.cpp` 只能封装 M3508 且构造时创建对象的限制。将 `joint.hpp` 的公共接口、映射、Motor adapter 和实现分开，公共接口不包含全部电机头。

规则是：**同一个物理闭环只有一个所有者**，而不是“所有 PID 都必须放电机里”。

- 默认底盘生成轮缘速度参考，由轮子执行器选择原生速度控制或本机速度环。
- 直接力矩控制作为显式能力/策略；不能在速度环后无意再套同一个速度环。
- 机械臂的关节空间跟踪、耦合控制、逆动力学留在 robotics；单关节原生 MIT 或本机伺服是具体执行方式。
- 当前底盘自己的轮速 PID 经 `SetTorque` 使用电机控制器，不能据此断言它已经重复闭环；重构要消除含混的控制权。
- 简单关节/轮子负责安装映射并委托执行器；耦合传动使用同一周期反馈快照，不能依赖逐个 Update 的顺序。
- 删除按 `joint id<3` 选择默认增益的逻辑（`joint.hpp:355`）；原生 MIT 不需要 host dt 时，应在执行策略里明确，不能让公共 PositionControl 参数悄悄失效。

传动应同时定义位置、速度、力/力矩和增益的坐标域。对于线性映射 `q = A·θ + b`，理想无损情况下满足 `q_dot = A·θ_dot`、`τ_motor = Aᵀ·τ_joint`；减速器效率另行配置。转动关节使用 rad/N·m，移动关节使用 m/N，不把所有关节量都命名成 angle/torque。

DM/LZ 字段是否已经是输出轴物理量、扭矩字段究竟是电流还是 N·m，必须按型号/固件资料和已知帧核实。当前换算链可疑，不能仅凭名字决定再乘转矩常数或减速比。

## 7. MRLink：保留 C 核心，合并重复包装

MRLink 不是具体器件。通用帧解析、编码和类型发布移到 `component/communication/mrlink`；UART/FDCAN/USB 通道实现属于平台适配。

`mrlink.c` 与 C++ 包装不属于同一层重复；`mrlink.hpp` 与 `mrlink_lite.hpp` 的 traits、slot、TopicResolver 和组织方式才需要收敛。默认采用固定容量、无运行期分配的一个类型封装；便利回调按需提供。latest-cache 复用通用容器，不再长出另一个消息中心。

优先修复以下契约与实现，再迁移目录：

- `Parse` 声明返回一帧，实际找到首帧后继续扫描，可能丢弃后续帧并覆盖 payload（`mrlink.c:216`）。提供真正的 ParseOne，以及有帧数/时间预算的 Dispatch。
- PushBytes 可在 ISR 调用，溢出却直接执行错误回调（`:354`）；与“回调在任务上下文”的文档冲突。默认延迟到 poll/dispatch 处理。
- 公开 1024 字节 opaque union 与内部布局分离（`mrlink.h:207`），需统一大小和对齐，验证 32/64 位，不能继续堆 magic number。
- C typed callback 不应强转未保证对齐的 byte buffer；使用 bytes + memcpy/codec。
- C++ 的 trivially-copyable 不代表稳定线协议。定义明确的大小端、字段、版本与 MessageTraits/codec，保留已部署格式的兼容边界。
- UART DMA 发送期间共享 TX buffer 可能被下次发布覆盖（`mrlink_channel_uart.c:327`）；明确 busy/排队/完成与缓冲所有权。
- UART PopRx 空间不足时会截断并丢弃剩余数据（`:308`）；维护偏移或显式失败。
- 注册失败要回滚，静态注册表需明确生命周期或支持解绑，FDCAN 的有效载荷限制进入配置校验。

## 8. `robotics` 的优化

### 底盘

保留 `ChassisKinematics` 注册时选择模型的现有方向，不再增加按车型复制的 module 控制器。

- 四轮顺序、数组类型、MaxAbs/Scale 收敛为公共类型/工具。
- 当前公式输出轮缘线速度 m/s，头注释却称 rad/s（`mecanum_chassis.hpp:13`）；统一成明确的线速度契约，轮半径转换只做一次。
- `wheelbase_m/trackwidth_m` 当前用于半轮距，配置命名或换算必须明确。
- 混合底盘只依赖公共类型，不通过包含另一个车型的完整实现获取工具。

### 机械臂与几何

FK、Jacobian、IK、动力学、规划、安全限制和机器人控制策略保留。现有 host 测试有实际解析值和有限差分验证，应保留并按职责整理。

- `Transform/Twist` 转换目前是平移 + 旋转向量打包（`transform.cpp:37`），不是 SE(3) exp/log。先准确命名；真正需要后者时提供独立接口，不偷偷改变插值语义。

- 无效轴/四元数不应静默伪装为成功的单位旋转；提供可检查状态。
- 约 610 行的 `ArmController` 保留统一门面，内部拆规划、跟踪、IK 降级、重力/安全策略；不能因有状态就搬到设备模块。
- 位姿 IK 降级为仅位置需显式配置并报告降级；流式控制只限制速度而把加速度置零，不能宣传为加速度受限。
- 明确 CartesianPlanner 使用的坐标系、速度定义、旋转误差和混合移动/转动关节的尺度。
- model、workspace 和控制器的生命周期必须明确。数值求解缓存和性能优化放在语义验证之后。

## 9. `module` 的优化

### 9.1 Chassis：一个入口，模型与策略分别选择

`module/chassis/chassis.hpp` 已有统一入口、设备接口、生命周期和故障处理，是可用的起点，但还需完善命令超时、反馈新鲜度、注册校验和控制权。

两个旧的 `mecanum.*` 与 `front_omni_rear_mecanum.*` 不是无价值重复；其中还含新入口没有覆盖的行为。先分出以下能力，再删除旧完整控制器：

| 原有行为 | 目标归属 |
| --- | --- |
| 运动学布局差异 | robotics 模型 |
| 加减速规划、速度/位置保持、滤波、静摩擦前馈 | 可选控制策略，复用 component，由底盘配置组合 |
| 朝向保持、跟随/旋转等可复用模式 | 明确输入的底盘控制策略，外部姿态/参考通过参数传入 |
| 高杆状态切增益、随机转动触发、遥控拨杆含义 | app 或具体项目 preset |
| 电机创建、CAN 初始化、旧 C MOTOR_RM_Ctrl | 移到装配/设备/总线调度，模块内删除 |

首个实现选择清楚的一条默认控制路径，不为了容纳所有设想建立策略插件系统。保留旧功能应有明确行为测试或项目需求；用户已删除的整机业务不重建。

### 9.2 Arm：去掉三关节和具体电机绑定

当前 `arm.hpp` 包含 CMSIS；`arm.cpp` 查询已删除的 Config、初始化 CAN、读取 OS queue；`ArmOutputAdapter` 固定创建 LZ RSO3、DM J4340 和 DM J4310P。它仍是项目机械臂，而非通用模块。

目标是固定容量 `Arm<N>`，注册模型、模块配置和 `JointDevice*` 数组，不强求运行时动态 N。

- `arm_model_config.*` 中实际机械尺寸、质量、COM、工具偏移移项目模型配置；通用的模型构造/校验留 robotics。
- `arm_control_types.h` 拆开设备配置、模型参数、模块策略和项目遥控参数，不再直接拉入厂商 C 电机头。
- `arm_command_adapter.*` 中遥控死区、拨杆积分和具体工作空间操作映射移 app；可复用的坐标变换/位姿增量保留纯接口。
- `arm_output_adapter.*` 改为关节数组执行参考，设备负责安装映射和能力检查，不按三个 index switch 厂商对象。
- 模块不读取 RTOS queue，不初始化总线，不从全局 Config 获取参数；由外部 `SetCommand` 和周期调用驱动。
- 初始化、使能、反馈、计算、输出入队失败都有明确状态；提交失败不只写 debug flag。

### 9.3 CloudMusic

播放器、整机告警、遥控音乐菜单和曲库不是一个职责。

- PWM 发声留 device；非阻塞播放只接受 score、play/pause/next 等普通命令。
- 当前播放器包装基本委托 Buzzer_Player，不维护第二套播放状态机。
- `cloudmusic.h` 对 DR16 的依赖及 `.c:590` 的拨杆约定移 app。
- `.c:98` 无条件包含全部曲谱及默认完整歌单，改为可选资源/示例，选择播放器不自动链接整个曲库。
- 统一 ms、OS tick 和秒的接口；纯播放器不调用 `osKernelGetTickCount`。

## 11. 公共接口必须先确定的契约

### 配置、生命周期与所有权

- C++ 公共接口以 C++17 为基线；保留 C 核心使用标准 C 可用接口，不无意依赖 GNU 宏或 C++20 语法。
- Config 只描述配置；构造函数不初始化总线、不发帧、不创建线程。
- 应用拥有设备、模型和模块；默认静态或调用方固定存储。模块保存非拥有引用，其对象寿命必须覆盖模块。
- `Register/Bind` 的含义统一为校验配置并绑定已准备好的对象。板级初始化、反馈订阅、设备初始化和显式使能由装配流程完成一次。
- 不从 module→wheel→motor 重复注册/初始化同一物理设备。需要代理启动时，必须有明确的独占约定。
- 验证重复设备、地址冲突、能力不匹配、非法映射/耦合和容量。失败不能留下半注册实例；回滚或明确标记失败。
- 内部持有自指针、固定槽或 placement-new 状态的对象，禁止未经定义的复制/移动。

### 命令、反馈与错误

- 命令与反馈分开类型，不用一个全局结构兼任目标、状态和配置。
- 命令携带发布时间/有效期；反馈携带接收时间、sequence 和字段有效性。时间戳使用同一单调时钟，明确单位、回绕处理和起点。
- sequence 改变表示新帧，online 由时间判断；不能把“读取成功”当作“本周期收到新帧”。不同反馈频率不要求每周期都有新帧。
- Step 接收明确的 `now` 和 `dt_s`；时间来自调用方，测试可以完全注入。
- 不支持的控制模式明确返回 Unsupported；无效配置不能静默换成经验值。限幅、正常禁用、无数据、超时和故障分开表达。
- 使用少量通用状态码加领域详情，避免一个覆盖所有业务的巨大错误枚举。
- 命令过期、反馈离线或输出失败后采用显式配置的安全行为。自由下落风险的机械臂不能一律照搬底盘的零力矩回退。

### 每周期执行与收发

```text
收取总线帧
  → 产生本周期设备反馈快照
  → app 输入映射 / 命令仲裁
  → module + robotics 计算参考
  → 对应执行器转换 / 唯一闭环控制
  → 准备待发送帧
  → 总线在确定位置统一 Flush
```

`Commit/Queue` 必须区别“接受进入发送队列”和“硬件已发送完成”。异步缓冲在完成前不能复用。RM 分组输出按总线/组统一提交；模块和单个电机不能各自刷新同一组。

一次故障后是否实际发送了禁能/零输出，要在总线行为上可验证；不能仅由一个 relax 标志证明。

下面仅表示手工装配的目标语义，不是已经存在的 API：

```cpp
// 装配一次：板级资源、设备、安装映射、模型和模块。
board.Initialize();
motor.Configure(motor_config, board.can);
wheel.Configure(wheel_config, motor_drive);
chassis.Bind(chassis_config, wheels);  // chassis_config 选择 robotics 模型
devices.Initialize();
devices.Enable();
chassis.Enable();

// 周期调用：由 app 决定频率和线程。
bus.ServiceRx(now);
devices.Refresh(now);
chassis.SetCommand(command);          // command 含有效期
chassis.Step(now, dt_s);
devices.Step(now, dt_s);
bus.Flush();
```

这些动作可以是普通对象调用和固定数组遍历，不要求新建万能 `Devices` 管理器。机械臂对应绑定 `ArmModel<N>` 和关节引用数组。

| 目标工程 | STM32 真实 HAL/CMSIS 编译；H7 中断/DMA/cache；各设备使能/禁能/断联；控制方向、尺度和极限；最终实机审核 |

必须保留为待资料/实机确认，而不是凭源码猜测修好的事项：DM/LZ 各型号协议物理量与量程、是否已包含内部减速；实际 HAL 的 DLC 表示；机械传动耦合和力矩映射；H7 DMA/cache；机械臂故障安全策略。

本阶段最终交付应是：一套职责清楚、能手工装配、行为经过验证的 `User` 库。届时项目引入整个 MRLib 作为依赖，但只链接所用能力；项目自己的 `board/`、`app/` 和未来的 `generated/` 位于项目侧。YAML 选择和生成装配，不复制或重写库算法。
